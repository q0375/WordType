# 二、论文撰写过程中拟采取的方法和手段

> **定位**：本节说明论文撰写阶段拟采用的研究方法、技术手段、验证方案与工具支撑，回答"研究怎么落地、结论靠什么支撑"这一问题。
>
> **写作原则**：本节所有方法与手段均**非纸面设想**，而是与系统中已实际建立的方法学设施一一对应。凡涉及已完成的验证工作，均标注可追溯的事实依据；凡属于拟开展的实验，均明确标注为待执行并给出实验设计。

---

## 2.1 总体研究思路与技术路线
本课题属**应用研究与系统实现相结合**的类型，研究范式为"**问题导向的工程实现 + 面向关键假设的对照验证**"。整体技术路线分五个阶段推进：

| 阶段 | 主要工作 | 产出物 | 阶段判据 |
|---|---|---|---|
| 第一阶段：文献与需求调研 | 梳理记忆科学领域的核心结论；盘点现有词汇学习产品的功能形态与不足；界定本系统的功能边界与设计口径 | 文献综述、需求规格说明书 | 核心概念定义统一，功能清单闭环，无二义性表述 |
| 第二阶段：系统设计与实现 | 完成架构、数据库、接口、UI 四层设计文档；完成编码实现与本地调试 | 架构设计文档、数据库设计文档、接口规范、UI 规范、可运行系统 | 全链路冒烟测试通过，九大模块功能闭环 |
| 第三阶段：一致性验证与质量保障 | 建立跨语言判定一致性校验机制、功能正确性验证脚本、性能与并发压力测试 | 一致性校验脚本集、测试报告 | 全部校验脚本零差异通过 |
| 第四阶段：应用与数据积累 | 部署至真实服务器环境并投入使用，积累真实使用数据 | 部署记录、过程性数据集 | 数据量满足统计分析的最小样本要求 |
| 第五阶段：数据分析与论文撰写 | 开展对照分析，归纳结论与创新点，完成论文各章撰写 | 分析报告、毕业论文 | 结论均有数据或文献支撑，无推断替代实证 |

**技术路线上的关键取舍**：本课题的技术难点不在功能实现，而在**"判定与计分口径的跨语言一致性"**与**"反馈粒度对记忆效果的影响"**两项。因此研究方法的设计也相应聚焦于此——前者以工程手段保证正确性（见 2.4），后者以实验手段获取证据（见 2.3）。

## 2.2 研究方法

### 2.2.1 文献研究法

**用途**：确立本课题的理论基座，避免工程设计脱离记忆科学已有结论。

**实施方式**：

1. **分层检索**：按"记忆基础理论（遗忘规律、元认知）→ 学习技术有效性（提取练习、分散练习、合意困难）→ 词汇教学策略（深加工、双编码、关键词联记）→ 数字化学习系统（间隔重复算法、智能导师系统、移动学习、游戏化效应）→ 专项（打字/书写与正字法能力、阅读流畅度）"五个层次展开检索，避免只检索"背单词软件"这类应用性文献而缺乏理论支撑；
2. **经典文献确定**：优先采用认知心理学领域的奠基性文献与大规模元分析作为理论支点，重点包括艾宾浩斯的遗忘曲线实验、间隔效应与提取练习的系列实证研究、学习技术有效性的大规模评估研究、双语词汇习得的编码策略研究等；
3. **文献管理**：按 GB/T 7714—2015 格式著录，建立文献台账记录每条文献的核心结论、本文引用位置与论点支撑关系，避免引而不用或用而不引。

**预期作用**：使系统的每一项算法设计（间隔推进规则、模糊反馈的保留、错误词的重新排期）都能追溯到具体的理论依据，而非经验设定。

### 2.2.2 需求分析法

**用途**：将记忆科学结论转化为可实现、无二义性的功能需求。

**实施方式**：采用**"决策编号化 + 双向可追溯"**的需求管理方法：

1. 对每一项存在争议或存在多种方案的设计决策，赋予唯一编号（如 D1、D2……D34），该编号在需求文档、代码注释、口径文档、设计文档中保持一致；
2. 每条决策记录**决策内容、决策理由、备选方案与放弃原因、影响范围**四项内容；
3. 每条决策**向下追溯到数据库字段、接口契约、代码位置与校验脚本**，向上追溯到对应的理论依据或现实约束。

**预期作用**：论文中论及任何一项设计选择时，均可给出完整依据，避免"设计意图无法自证"的问题。经审阅，本系统在开发过程中累计形成三十余项此类决策记录，构成本设计的方法学基础。

### 2.2.3 面向关键假设的对照实验法

**用途**：这是本课题**最关键的方法**——系统中的若干设计主张（如"保留模糊反馈优于纯二元判定""游戏分数与记忆能力同构""复习队列分层优于无优先级"）属于设计假设，必须以实验数据支撑，不能以设计意图代替实证。

**实验设计要点**：

| 实验 | 自变量 | 因变量 | 对照设置 | 拟验证的假设 |
|---|---|---|---|---|
| **实验一：反馈粒度的影响** | 反馈形式（三档模糊判定 / 纯二元判定） | 学习后 7 天、14 天、30 天的保持率（一次性回忆正确率） | 同一词库、同一词表随机分为两组，采用相同的学习—复习时间表 | 提取练习中保留"近似"档（合意困难）相比纯二元判定，能带来更优的长期保持 |
| **实验二：调度策略的影响** | 复习队列组织方式（分层优先级 / 无优先级全序） | 单位时间内的复习量与 30 天保持率 | 相同词表、相同总学习时长 | 将逾期与高危词前置，可提升单位时间记忆收益 |
| **实验三：游戏化的耦合度** | 游戏得分构成（与打字能力同构 / 与操作次数耦合） | 实验组的学习时长、复习完成率 | 分别设置"得分由准确率与速度决定"与"得分由击键次数决定"的对照 | 游戏化机制与学习目标同构时，才不会损害学习效果 |
| **实验四：AI 建议的有效性** | 建议来源（规则引擎 / 大模型） | 建议的事实正确性、可执行性、采纳率 | 固定同一份数据上下文，两种引擎各生成 N 次，评审维度盲评 | 规则引擎在**可执行性**上优于大模型，大模型在**语义连贯性**上优于规则引擎 |

**实验实施要求**：

1. **样本与分组**：采用随机分组，两组在词表、初始熟练度、每日学习时长上保持一致，以控制无关变量；
2. **保持率测量**：采用一次性回忆测验（不给选项、直接默写），而非再认测验——因为再认会显著高估保持水平，无法反映真实的提取能力；
3. **数据记录**：系统已支持导出完整的学习过程数据（含逐次复习时间戳、判定结果、按键级反应时），可支撑长期跟踪测量；
4. **诚实声明**：本课题的实验样本量受真实使用人数限制，**属于小样本探索性验证，不足以支撑强因果推论**。论文中所有结论均将明确标注样本量与适用边界，不将探索性结论表述为普适规律。

> **方法论立场说明**：这一自我限定是必要的。本系统的用户规模属小样本，若过度声称实验结论的普适性，反而会成为答辩环节的薄弱环节。将结论准确定位为"在有限样本下的初步验证"，比夸大结论更为严谨。

### 2.2.4 比较分析法

**用途**：在缺乏严格实验条件时，通过结构化对比获得可辩护的分析结论。

**实施方式**：选取同类词汇记忆产品（国际与国内各选取若干），从以下维度作结构化比较：

| 比较维度 | 比较要点 |
|---|---|
| 记忆调度机制 | 排期依据、是否可解释、是否可调校、算法是否公开 |
| 反馈形态 | 二元判定 / 分档判定 / 连续量化，及各形态的适用场景 |
| 题型设计 | 是否支持多模态（视觉/听觉/语义）与提取练习 |
| 激励设计 | 游戏化机制与学习目标的耦合程度 |
| 组织层面支持 | 是否提供班级度量、考核、过程性监控 |
| 数据可获取性 | 学习过程数据是否可导出、学习者能否自主复盘 |

**预期作用**：本系统已积累一份**基于真实使用过程的体验评估报告**（完整走通全部功能流程后形成），可作为比较分析中"实际使用体验"维度的第一手材料，避免对比结论沦为产品宣传的转述。

## 2.3 数据采集与分析手段

### 2.3.1 过程性数据采集

本系统的一个根本优势在于：**数据采集不是事后附加的统计功能，而是业务的副产品**。系统在四个模块的学习行为中均落库打字记录（含正确率与反应时），逐日落库活跃度（新增词数、复习数、正确数、错误数），考核与游戏行为落库完整的过程明细。这一设计使得学习过程天然可分析，无需学习者额外配合。

**采集内容分类**：

1. **结果性数据**：每个词的判定结果、复习轮次、当前熟练度、间隔天数——用于分析记忆状态分布；
2. **过程性数据**：首次按键时间、逐键反应时、准确率、连续正确数——用于分析学习者的**困难定位**（哪些字母组合、哪些词是瓶颈）；
3. **行为轨迹数据**：每日学习时段分布、连续活跃天数、复习时段分布——用于分析学习习惯；
4. **异常数据**：考核失焦次数、单题反应时异常值——用于评估考核过程的可信性。

### 2.3.2 数据分析方法

- **描述性统计**：熟练度分布、逾期天数分布、错误率随复习轮次的衰减曲线，用于刻画学习者的记忆状态结构；
- **趋势分析**：打字速度与准确率的时间序列趋势（按日聚合），用于观察技能与记忆的相互影响；
- **对照比较**：按 2.2.3 的分组设计进行组间比较；
- **归因分析**：结合错误词表与弱字母组合统计（如指法层面的薄弱环节），定位学习瓶颈的具体成因；
- **系统日志分析**：利用系统保留的可审计字段（如建议生成失败时的回退原因记录）进行可靠性分析。

### 2.3.3 已具备的实证材料

本系统在开发与运行过程中已积累了可用于论文分析的第一手材料：

| 材料 | 内容 | 论文用途 |
|---|---|---|
| 大模型建议 vs 规则引擎实测对比 | 含真实上下文输入、两种引擎的实际输出、差异归因与样本局限声明 | 实验四的先导对比与契约缺陷分析（该对比已直接产出一项设计改进） |
| 规则引擎连续多日失败与自动回退的记录 | 失败原因可追溯，且功能未中断 | "AI 功能的降级设计有效性"案例 |
| 产品体验评估报告 | 完整走通全流程的第一手体验记录 | 比较分析中"实际使用体验"维度 |
| 系统全面体检报告 | 全链路排查结果 | 工程质量与遗留问题的诚实披露 |

> **重要原则**：论文中凡引用上述材料，均以"已观测到的事实"表述，并同步呈现其局限（如样本量、对比非同一输入等），**不以工程团队内部材料冒充受控实验结果**。

## 2.4 技术手段与验证方案

本节是本节内容的重点。针对上文识别的两项技术难点，说明拟采取的保障手段。

### 2.4.1 跨语言判定一致性保障（本课题最核心的技术手段）

**问题性质**：为保证交互体验，系统必须在后端（Python）与前端（TypeScript）各实现一次判定逻辑以实现零延迟的前端预判定。跨语言复刻存在大量隐性差异来源——编辑距离的提前退出条件、序列相似度算法的匹配表构造与匹配块合并逻辑、空格与大小写的处理方式、自动匹配垃圾字符的开关等。任何一处漂移都会导致"界面显示正确、服务端记错分"的不一致。这类缺陷**极其隐蔽**：功能测试全绿，用户却已按错误结果形成了错误的学习记录。

**采取的手段**：以工程手段将"隐性缺陷"转化为"可自动拦截的显性失败"。

1. **单一口径源头**：所有判定阈值与默认值集中于唯一的配置文件，其余模块一律引用，**禁止在业务代码中就地写字面量**。口径变更只需修改单一文件；
2. **逐位等价复刻**：前端不是"近似实现"算法，而是复刻后端算法的内部流程，包括序列相似度的字符频次表构造、最长匹配块查找、相邻匹配块合并等中间步骤，并明确定义了半进位取整规则（因编程语言内置的舍入函数行为差异会导致 ±1 漂移，必须显式对齐）；
3. **对拍校验脚本**：编写跨语言对拍脚本，对同一批样本输入同时执行两端实现并逐一比对输出，**出现任何差异即判定为失败**。系统已建成此类校验脚本七个，覆盖以下维度：

| 校验脚本 | 校验内容 |
|---|---|
| 判定边界矩阵 | 三档判定与连续得分比的全部边界情形 |
| 大小写敏感性 | 区分大小写与不区分大小写的差异验证 |
| 口径作用域隔离 | 验证各场景使用各自口径，且已废弃口径在代码中无残留 |
| 游戏公式一致性 | 时限公式、得分公式、血量公式、连击阶梯的两端一致性 |
| 下坠时限同源 | 从前端源码中提取公式与后端逐位对拍 |
| 时限 × 难度 | 真实开局—交卷流程下的服务端复核值与本地计算值比对 |
| 口径相关界面 | 界面文案与实际口径一致（自动化界面测试） |

4. **真实接口闭环校验**：部分校验不满足于纯函数测试，而是完整走通"开局 → 提交"真实流程，比对服务端复核结果与"前端同口径"本地计算结果，验证接口契约层面的正确性；
5. **变更强制触发**：将校验脚本定位为"改口径必跑"的强制环节，而非可选的质量保障措施。

**预期作用**：该机制使"判定口径的跨端一致性"从依赖人工谨慎，转变为可自动验证的工程属性。**这一方法本身即具备可迁移性**，对任何存在多语言实现的判定逻辑类系统均适用，是本文认为最具方法论价值的部分之一。

### 2.4.2 功能正确性验证

**采取的手段**：分层测试体系，覆盖不同层级的正确性风险。

| 层级 | 验证方式 | 覆盖内容 |
|---|---|---|
| 全链路 | 冒烟测试 | 注册登录、幂等重放、考核全流程、游戏全流程、防作弊校验、数据导出 |
| 导入链路 | 专项测试脚本 | 表头识别、单元策略、重复策略、编码探测、引号字段、错误行报告、万行级数据量、导出回环、权限控制 |
| 性能与并发 | 压力测试脚本 | 多线程并发请求、万行量级数据导入、导入串行化的互斥验证 |
| 接口一致性 | 幂等验证 | 重复提交不重复计分（头幂等）、单题作答去重（体幂等） |
| 界面行为 | 自动化界面测试 | 关键交互路径、快捷键行为、确认拦截行为 |

**测试数据处理原则**：所有测试脚本均自行创建并回收测试数据；对可能触及既有数据的操作，**在执行前先关联查询账号归属与注销状态进行核对**，确认是测试数据后才执行删除，避免误删真实数据。

### 2.4.3 可靠性与数据一致性手段

**问题性质**：单机部署架构下，需应对弱网重试、并发作答、客户端数据不可信、数据库备份完整性等风险。

**采取的手段**：

1. **幂等中心**：所有关键写操作建立统一的幂等机制（幂等键 + 端点标识 + 状态码 + 响应快照，保留期内去重），并在单题作答层面追加请求级去重，从根本上消除重复计分；
2. **服务端权威记账**：客户端上报的分数、耗时等数据一律不被直接采信，服务端依据逐词日志重新计算；对速度类数据设定有效性阈值与上限过滤（如极短耗时视为误触无效、超高值视为异常），阻断瞬时异常值污染统计；
3. **数据一致性设计**：熟练度等累计值采用数据库端增量更新（`SET x = MIN(上限, x + delta)`），天然规避读—改—写模式的并发竞态；时间戳统一以服务端为唯一源头，规避客户端时钟偏差与篡改；
4. **备份完整性**：数据库备份采用数据库原生的备份接口而非文件复制——文件复制在数据库运行期间只能获得上一次检查点之后的数据，可能得到不完整的快照；
5. **部署安全基线**：公网部署时若检测到默认密钥配置则拒绝启动；用户自有凭据采用认证加密存储。

### 2.4.4 可视化与图表工具

论文中的数据呈现拟采用以下工具与规范：

- **系统界面截图**：呈现功能形态与交互细节，截图统一标注版本与时间，避免版本混淆；
- **架构图与流程图**：采用标准化建模语言绘制，保证图与实际实现一致（而非画一张理想化的架构图）；

- **代码与数据引用**：论文中涉及关键算法与实测数据时，标注具体的文件位置与记录来源，保证可追溯与可复现。

## 2.6 研究方法的可靠性论证

为避免方法本身成为薄弱环节，本节对所采用方法的可靠性作简要论证。

**1. 所用方法与研究问题的匹配性**

| 研究问题类型 | 适配方法 | 匹配理由 |
|---|---|---|
| "记忆规律如何落到系统设计" | 文献研究法 + 需求分析法 | 设计需可追溯至理论，且需消除二义性 |
| "判定口径是否真的两端一致" | 对拍校验（实证验证） | 这是可直接验证的事实命题，以自动化验证作答最有力 |
| "某种设计是否更优" | 对照实验法 | 属因果性命题，只能以对照实验获取证据 |
| "与同类产品相比处于什么位置" | 比较分析法 | 属描述性命题，无需严格实验 |
| "系统实际表现如何" | 描述性统计 + 日志分析 | 基于真实运行数据的事实呈现 |

**2. 避免循环论证的设计**

本课题在方法层面刻意设置了防线，防止"用设计证明设计"：

- 判定一致性不以"设计为双端复刻"作为结论，而以**对拍脚本的实际比对结果**作为结论；
- AI 建议引擎的优劣不以"设计了回退机制"作为结论，而以**连续多日失败后功能未中断的运行记录**作为结论；
- 学习效果不以"设计遵循了记忆科学"作为结论，而以**对照实验的保持率数据**作为结论。

**3. 已知方法局限与应对**

| 局限 | 应对策略 |
|---|---|
| 真实用户规模有限，难以获得大样本 | 明确声明为小样本探索性验证，结论限定适用边界，不做普适性推断 |
| 难以进行双盲对照（用户已知自己在被实验） | 至少保证分组随机与基线一致，并诚实说明无法双盲这一残余混淆因素 |
| 长周期保持测量存在流失 | 提前设计测量时点（7/14/30 天）并尽可能在用户活跃期内完成；流失情况如实报告 |
| 现有产品不公开算法细节，比较分析受限 | 比较结论限定在"可公开观察的功能形态"层面，不推测其内部算法 |
| 部分对比材料为系统运行日志而非受控实验 | 严格区分"已观测事实"与"受控实验结论"，论文中分别表述 |
